# 宠物添加流程（ROCO REMAKE）

> 严谨可复用的宠物添加机制。每次新增宠物严格按此流程执行。

## 流程（4 步）

### 第 1 步：玩家提供技能文本
玩家以任意形式提供宠物的技能介绍文本（宠物名、定位、血脉、技能效果、数值）。

### 第 2 步：转化为机器可读规格
- 生成 `specs/pet_{{英文短名}}.md`，严格套用 `specs/PET_TEMPLATE.md`
- 转化原则：**忠实原文，不增删机制**；逐字保留效果描述后结构化
- 任何歧义、矛盾、缺失数值 → 在文件相应位置标 `[疑问]`，并用 ask 询问玩家
- 规格完成后告知玩家文件位置，等待玩家确认规格（或直接进入第 3 步，视玩家意愿）

### 第 3 步：在游戏中实现
- 编辑 `ROCO REMAKE.html`：
  1. 注册宠物数据（DEFAULT_PETS：id/名称/系别/emoji/等级/种族值/技能表/血脉）
  2. 注册技能数据（DEFAULT_SKILLS：威力/PP/先手/命中/分类/onUse 实现）
  3. 实现血脉逻辑（bloodline 或 onSkillUse 触发）
  4. 若依赖引擎未实现机制 → 先与玩家讨论（见下），确认后再实现或标记 UNSUPPORTED
- 实现时保持与既有技能风格一致（ctx 上下文 API、消息文案中文）

### 第 4 步：自检（必须全过才结束）
1. **静态检查**：JS 语法（node --check）、括号平衡、函数无重复定义
2. **规格核对**：宠物/技能/血脉与规格文件逐条一致（id、数值、效果）
3. **机制核对**：规格「机制依赖清单」每项 → 在代码中定位实现点
4. **逻辑走查**：模拟关键回合（技能使用→效果触发→回合结算），确认无死循环、无 NaN、无错误覆盖
5. **git 提交**：规格文件 + 游戏文件一起提交（本地，不自动推送）
6. 报告：宠物名、实现要点、自检结果、遗留问题

## 问题处理规则（第 2-4 步中发现问题的处理）

| 问题类型 | 处理方式 |
|----------|----------|
| 机制 bug（实现后自检发现） | 修复；无法本地修复则报告玩家 |
| 机制无法实现（引擎缺失） | **ask 玩家**：实现引擎能力 / 简化机制 / 标记 UNSUPPORTED 暂缓 |
| 机制自相矛盾（文本内部冲突） | **ask 玩家**：让玩家裁定哪条优先 |
| 数值缺失 / 模糊（如"较高威力"） | **ask 玩家**：给出具体数值或由我按模型预设并标注 |
| 与既有机制冲突（如环境覆盖规则） | **ask 玩家**：确认覆盖优先级 |
| 歧义（可多解） | **ask 玩家**：提供选项 |

> 规则：**不确定就停**。任何影响机制理解的疑问，未得到玩家答复前不擅自实现。

## 规格文件存放
- `specs/pet_{{短名}}.md`：宠物规格（每宠一份）
- `specs/PET_TEMPLATE.md`：模板（本流程引用）
- 规格文件随实现提交入库，作为机制文档留存
